# Подключение бесплатного бэкенда (Supabase)

Фронтенд уже готов: `src/services/supabase.ts` отдаёт `null`, пока бэкенд
не настроен, и приложение работает на localStorage. Ниже — что сделать,
чтобы поднять бесплатный бэкенд ($0, карта не нужна).

Лимиты Free (хватит на старт с запасом): 2 активных проекта, БД 500 МБ,
50 000 активных пользователей/мес, Storage 1 ГБ, 5 ГБ трафика/мес.
Важно: проект **засыпает после недели без активности** — для витрины,
которую открывают редко, это нормально (будится вручную в Dashboard);
для «всегда онлайн» позже понадобится Pro ($25/мес, только с твоего согласия).

## Шаг 1. Аккаунт и проект (~5 минут)

- [ ] Зарегистрироваться на https://supabase.com (можно через GitHub).
- [ ] Create organization → Create project:
  - Name: `beautybooking` (или `nail-studio`);
  - Database Password: сгенерировать и **сохранить** (нужен для прямых подключений);
  - Region: ближайший к клиентам — `West EU` / `Central EU`;
  - Plan: **Free**.
- [ ] Дождаться, пока проект станет Active (пара минут).

## Шаг 2. Применить схему БД (~3 минуты)

- [ ] В проекте открыть **SQL Editor → New query**.
- [ ] По очереди вставить целиком и выполнить (**Run**) все миграции из
      `supabase/migrations/`: `0001_init.sql`, `0002_service_category.sql`,
      `0003_telegram_notifications.sql`, `0004_guest_booking_rpc.sql`.
      0004 обязательна: без неё публичная запись не работает (гостям закрыт
      прямой доступ к чужим данным, всё идёт через RPC).
- [ ] Проверить: Table Editor показывает таблицы `businesses`, `services`,
      `clients`, `appointments`, `working_hours`, `blocked_periods`,
      `reviews`, `media`, `notification_settings`. Повторный прогон безопасен.

## Шаг 2½. Keep-alive от автопаузы (2 минуты, опционально но желательно)

Free-проект засыпает после ~недели **низкой активности базы**. Важно понимать,
как Supabase это считает (официальные доки):

- Считается **активность базы**: запросы к БД, API-вызовы, обращения от сайта,
  визиты в дашборд. Ориентир: «a few user requests to the database each day».
- **Вход в учётку не обязателен**: живой сайт сам будит базу — каждая открытая
  страница делает запросы (услуги, работы...). Спит только сайт, который неделю
  вообще никто не открывал.
- Перед паузой придёт **warning-email за неделю**, после — письмо о паузе.
  Пробуждение — 1 клик в дашборде, данные целы (окно восстановления — год).
- Pro ($25/мес) не засыпает никогда — только с твоего согласия.

Страховка уже лежит в репозитории: `.github/workflows/keepalive.yml` —
3 раза в сутки дёргает 2 лёгких чтения. Включи так:

- [ ] Репозиторий → Settings → Secrets and variables → Actions → **Variables**:
  `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (публичные значения,
  не секреты; те же переменные использует деплой).
- [ ] Actions → выбрать `Supabase keep-alive` → Run workflow (проверочный прогон).

Что уже внутри миграции:
- все сущности с `business_id` (multi-tenant по AGENTS.md §6);
- **триггер против двойной записи** — пересекающиеся записи одного бизнеса
  отклоняются сервером (`SLOT_TAKEN`), не только проверкой во фронтенде;
- дедупликация клиентов по телефону в рамках бизнеса;
- RLS: гости читают публичное и могут создать запись, владелец
  (Auth user) видит/меняет только свой бизнес;
- бакеты Storage `avatars` и `works` (публичное чтение).

> Здесь v1: сайт одного салона, вход только для владельца.

- [ ] Аккаунт мастера заводится один раз в **Authentication → Users → Add user**

      расписание) настраивается из админки, дашборд не нужен.

## Шаг 4. Подключить фронтенд локально (~2 минуты)

- [ ] **Project Settings → API**: скопировать `Project URL` и **Publishable** key
  (`sb_publishable_...`, в новых проектах он вместо legacy `anon`).
  ⚠️ Только publishable. Secret-ключи (`sb_secret_...`) в браузер/репозиторий — никогда.
- [ ] В корне проекта создать `.env.local`:

```bash
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
VITE_USE_SUPABASE=true
```

- [ ] `npm run dev` — в консоли не должно быть варнинга `[supabase]`.
  Пока репозитории Phase B не написаны, UI продолжает читать localStorage —
  это нормально: шов проверен, данные не ломаются.

## Шаг 5. Деплой: переменные окружения

- [ ] На хостинге (Vercel / Cloudflare Pages / Netlify) добавить те же три
      переменные в Environment Variables production.
- [ ] Переделплоить. `.env.local` в git не попадает (см. `.gitignore`).

## Платформа: как устроен multi-tenant

Один деплой — много студий, форк под каждого мастера не нужен:

- `/` → флагманская студия (твой салон). Чья именно — задаёт `VITE_FEATURED_SLUG`
  в `.env.local` / переменных хостинга. После онбординга поставь туда свой slug
  и передеплой — главная станет твоей страницей.
- `/:slug` → публичная страница любой студии (профиль, услуги, работы, отзывы,
  запись). Данные грузятся по slug, разделение — по `business_id` + RLS.
- `/masters` → лендинг платформы («создай свою страницу»).
- `/register → /onboarding → /admin` → регистрация и кабинет мастера.
- Зарезервированные slug (`login`, `admin`, `masters`, …) выдавать нельзя —
  список в `src/utils/errors.ts` (`RESERVED_SLUGS`), онбординг их отклоняет.
