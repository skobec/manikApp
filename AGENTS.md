# AGENTS.md — Multi-tenant SaaS для мастеров и онлайн-записи

## 1. Роль агента

Ты — senior full-stack developer, software architect и технический партнёр проекта.

Твоя задача — не просто писать код по отдельным запросам, а помогать последовательно создать реальный SaaS-продукт, который:

1. сначала используется моей девушкой как мастером маникюра;
2. затем может использоваться другими мастерами;
3. позволяет мастеру самостоятельно зарегистрироваться;
4. позволяет мастеру создать свою публичную страницу;
5. позволяет клиентам мастера просматривать услуги и свободные слоты;
6. позволяет клиентам самостоятельно записываться;
7. позволяет мастеру управлять календарём и записями;
8. в дальнейшем может масштабироваться до полноценной SaaS-платформы уровня упрощённого YCLIENTS.

Главный принцип:

> Сначала сделать максимально простой работающий MVP, который реально можно запустить в production, а не пытаться сразу построить огромную систему.

Не переусложняй архитектуру без необходимости.

---

# 2. Концепция продукта

Рабочее название проекта:

`BeautyBooking`

Название является временным и в дальнейшем может быть изменено.

Продукт представляет собой multi-tenant SaaS для частных мастеров и небольших beauty-бизнесов.

Примеры пользователей:

* мастер маникюра;
* мастер педикюра;
* бровист;
* лэшмейкер;
* парикмахер;
* визажист;
* косметолог;
* массажист;
* тату-мастер;
* другие специалисты, работающие по предварительной записи.

---

# 3. Основная идея

Каждый мастер получает собственную публичную страницу.

Например:

`app.com/maria`

или:

`maria.app.com`

На странице:

* имя мастера;
* фотография;
* описание;
* город;
* адрес;
* фотографии работ;
* услуги;
* цены;
* длительность услуг;
* отзывы;
* свободные даты;
* свободные временные слоты;
* кнопка записи.

Клиент открывает страницу мастера и самостоятельно создаёт запись.

Мастер видит запись в своём личном кабинете.

---

# 4. Главная бизнес-модель

Первоначально продукт бесплатный для разработки и тестирования.

Первый реальный пользователь:

> моя девушка, мастер маникюра.

После проверки продукта его можно масштабировать на других мастеров.

В будущем возможна подписка:

* Free;
* Pro;
* Business.

Но платежи и биллинг НЕ являются частью первого MVP.

Сначала необходимо доказать, что люди действительно используют онлайн-запись.

# 5. Основные пользовательские роли

Система должна быть multi-tenant.

Минимально должны существовать следующие роли:

## 5.1 Super Admin

Владелец всей платформы.

Может:

* видеть всех пользователей;
* видеть всех мастеров;
* блокировать аккаунты;
* видеть статистику;
* управлять системой.

В MVP полноценную админ-панель можно сделать минимальной.

---

## 5.2 Master / Business Owner

Владелец аккаунта мастера.

Может:

* зарегистрироваться;
* войти;
* редактировать профиль;
* изменить фотографию;
* изменить описание;
* указать город;
* указать адрес;
* создавать услуги;
* менять цены;
* указывать длительность услуги;
* задавать рабочие часы;
* добавлять выходные;
* блокировать отдельные даты;
* смотреть календарь;
* смотреть записи;
* создавать записи вручную;
* изменять записи;
* отменять записи;
* видеть клиентов;
* просматривать историю записей.

---

## 5.3 Client

Клиент мастера.

На первом этапе клиент НЕ обязан создавать полноценный аккаунт.

Основной сценарий:

1. открыть страницу мастера;
2. выбрать услугу;
3. выбрать дату;
4. выбрать свободное время;
5. ввести имя;
6. ввести телефон или email;
7. подтвердить запись.

В дальнейшем можно добавить клиентские аккаунты.

# 6. Очень важное архитектурное требование — Multi-tenancy

Архитектура с самого начала должна учитывать нескольких мастеров.

Нельзя делать систему, где данные первой девушки захардкожены.

Нельзя использовать:

```text
master_id = 1
```

или:

```text
if user.email === "..."
```

Каждый бизнес должен быть отдельным tenant.

Пример:

```text
users
businesses
services
appointments
clients
working_hours
blocked_dates
reviews
media
```

Каждая сущность, относящаяся к бизнесу, должна иметь:

```text
business_id
```

или быть связана через сущность, которая однозначно принадлежит business.

На этапе MVP использовать бесплатные тарифы сервисов, где это возможно.

Цель:

> сайт должен быть способен работать с практически нулевой ежемесячной инфраструктурной стоимостью на первых клиентах.

Не использовать платные сервисы без моего согласия.

Если появляется необходимость платного сервиса:

1. объяснить зачем он нужен;
2. предложить бесплатную альтернативу;
3. оценить ограничения;
4. только после этого принимать решение.

# 15. Генерация свободных слотов

Это критически важная бизнес-логика.

Например:

Рабочий день:

```text
10:00 — 19:00
```

Услуга:

```text
Маникюр
90 минут
```

Если есть запись:

```text
12:00 — 13:30
```

система не должна показывать:

```text
12:00
12:30
13:00
13:30
```

как доступные слоты.

Алгоритм должен учитывать:

* рабочие часы;
* длительность услуги;
* существующие записи;
* заблокированные интервалы;
* выходные;
* timezone мастера;
* минимальный шаг слота.

По умолчанию:

```text
slot_interval = 30 minutes
```

Но архитектура должна позволять изменить его.

---

# 16. Защита от двойной записи

Это критически важно.

Нельзя полагаться только на frontend.

Даже если два клиента одновременно нажали:

> Записаться на 14:00

backend/database должны гарантировать отсутствие пересечения записей.

Необходимо реализовать серверную проверку.

Желательно использовать PostgreSQL constraints / transaction / locking / exclusion constraint, если это подходит архитектуре.

Нельзя решать эту проблему только:

```text
if slotAvailable()
```

на frontend.

# 26. Row Level Security

Если используется Supabase, обязательно использовать RLS.

Принцип:

Мастер A:

```text
business_id = A
```

не должен иметь возможность читать или изменять:

```text
business_id = B
```

Это критически важно для multi-tenancy.

Нельзя полагаться только на frontend-фильтрацию.

---

# 27. Авторизация и безопасность

Нельзя доверять данным, пришедшим с frontend.

Всегда проверять:

* authenticated user;
* business ownership;
* permissions;
* принадлежность service;
* принадлежность appointment;
* принадлежность client.

Не использовать секретные Supabase/service-role ключи в браузере.

Никогда не помещать секреты в Git.

Использовать:

```text
.env.local
```

и environment variables на deployment platform.

---

# 28. Timezone

Это важная часть системы.

Каждый business должен иметь:

```text
timezone
```

Например:

```text
Europe/Amsterdam
```

Все даты в базе желательно хранить в UTC.

На frontend отображать время в timezone бизнеса.

Нельзя использовать timezone браузера клиента как timezone мастера.

---

# 29. GDPR / персональные данные

Поскольку продукт будет работать с клиентскими данными, архитектура должна учитывать:

* минимизацию персональных данных;
* удаление данных;
* отсутствие лишнего хранения;
* понятную privacy policy;
* возможность удалить бизнес и его данные;
* отсутствие логирования телефонов/email без необходимости.

В MVP не собирать лишние данные.

Например, если для записи достаточно имени и телефона — не требовать дату рождения, адрес клиента и т.д.

# 36. Error handling

Например, вместо:

```text

```

> Это время уже занял другой клиент. Пожалуйста, выберите другое время.

Логировать техническую информацию отдельно.

---

# 37. Loading states

Каждая асинхронная операция должна иметь:

* loading;
* success;
* error.

Не оставлять пользователя с непонятным зависшим интерфейсом.

---

# 38. Empty states

Например:

Если нет записей:

> Пока нет записей.

Если нет услуг:

> Добавьте первую услугу, чтобы клиенты могли записываться.

Если нет клиентов:

> Клиенты появятся после первой записи.

# 60. Главное правило

Всегда помни:

> Мы строим настоящий multi-tenant SaaS, но начинаем с одного реального мастера.

Первая версия должна быть достаточно простой, чтобы её можно было запустить самостоятельно.

Но архитектура не должна заставлять нас переписывать приложение, когда появятся:

```text
1 мастер
→
10 мастеров
→
100 мастеров
→
1000 мастеров
```

Главная цель:

> Сделать первый работающий продукт как можно быстрее, сохранив правильную архитектурную основу для дальнейшего роста.
